# SABT — Core Workflows

Version: 0.1

## Appointment
Free -> Reserved -> Present -> Done. Reserved may become Cancelled or No-Show. Additional transitions are controlled by appointment policy.

## Present
Appointment Type determines whether Present records attendance only or records attendance and starts/offers an Operation. Attendance is operational data and is audited.

## Operation creation
Operation may start from an Appointment or directly from Operations. Select Project and Operation Type, load configuration, collect core/custom fields, add dynamic-role parties, select Property, capture working snapshots, attach documents and enter workflow.

## Operation lifecycle
Base states: Draft -> In Progress -> Ready for Finalization -> Finalized. Operation Types may define additional states while respecting system safety constraints.

## Finalize
Validate required fields, parties, documents, restrictions, workflow prerequisites and concurrency. Create immutable final snapshot, allocate Registration Number where applicable, persist atomically, record audit and block ordinary edits.

## Correction
Finalized Operation -> Correction Request -> Approval -> New Version -> Finalization. Previous finalized version remains immutable.

## Contract
An Operation may produce zero or one Contract. User enters Contract Number manually; configured uniqueness policy is checked. Property is required. Registration Number is generated by policy. No payment processing occurs.

## Restrictions
Import CSV/XLSX or clipboard data, map columns, validate, preview, import batch and audit. During processing, active rules are evaluated. Warning rules show warnings; blocking rules stop the operation unless override permission exists. Overrides require a reason and audit.

## Documents
Upload, scan/import and enter metadata. Replacement makes the new file current and audits the replacement. Archive is logical. Physical deletion is restricted to Admin and audited.

## Forms/PDF
Business data -> selected template -> fields/logo/QR -> PDF -> preview/print. Designer uses millimeters; renderer converts to PDF points.

## QR
Configuration defines selected data, payload version, placement, size, error correction and checksum/signature policy. V1 does not require a public verification site.

## Reminders
Rule-based reminders can target appointments, define timing, trigger event, recipient/role, message, severity and suppression/repeat behavior. Candidate triggers include shift start, previous-day end and application opening.

## Backup/Restore
Backup includes database, documents, generated PDFs, templates and branding/settings. Automatic/manual backup and rotation are supported. Restore is Admin-only: validate backup, create pre-restore backup, confirm, restore, validate and audit.

## Concurrency
Normal edits use optimistic concurrency. Sensitive forms may use short-lived application locks. Version conflicts are shown to the user; silent overwrites are prohibited.


## Parent Contract and transfer workflow — proposed

### Create/import Parent Contract
1. Select the Project (its two-digit code must be from `10` onward; `01`–`09` are invalid). Enter the four-digit member/contract suffix manually, or import a six-digit Parent Contract number from Excel/CSV. The two-digit Project code is shared by all members/contracts in that Project. The import file may also include optional unit/property details and initial owner/member information.
2. Validate that the six-digit number begins with the selected Project's two-digit code, the suffix is four digits, numbers are unique, required fields are present, and any supplied people/property/unit references are resolvable.
3. Preview all rows and errors before confirmation. On confirmation, persist the accepted batch transactionally and record an import/audit report.
4. Preserve imported business numbers; do not silently renumber historical records.

### Register a transfer
1. Open the Parent Contract and start a new transfer Operation, or find the parent by number and start from its transfer history.
2. Capture the transfer's parties (including prior/new owner roles), property context, documents, custom fields, and workflow data.
3. Allocate the next child number under the parent using transactional sequence state. Do not calculate it with `MAX()+1`; gaps from cancelled or rejected records must not cause number reuse.
4. Finalize only after configured validation succeeds. The transfer's finalized snapshot preserves the business state at that point.
5. Only a transfer in the agreed ownership-effective state changes the derived current-owner summary. Draft, rejected, or cancelled transfers do not.
6. A later real transfer creates another Operation. A correction to an already finalized transfer uses the correction/version process and preserves the old version.

Current implementation allocates the child sequence transactionally during transfer finalization; issued numbers are not reused, so gaps are expected. Child numbers are positive decimal integers without zero padding. Ownership is derived only from valid finalized transfers containing the `BUYER_TRANSFEREE` role. Legacy import ordering and duplicate Person/Property matching remain open; do not infer either silently.

### Search and transfer history
- Searching by a six-digit Parent Contract number returns the parent summary and its authorized transfer history.
- Child rows are ordered by transfer sequence, with dates and status displayed separately; sequence is the canonical business ordering when legacy dates are inconsistent.
- Selecting a child opens its detail page, including parties, documents, workflow/audit history, and immutable finalized snapshot.
- The parent summary shows the initial owner separately from the derived current owner and makes the derivation traceable to the latest valid finalized transfer.
- Search and detail access must enforce Project access and authorization on the server; hiding a row in the UI is not a security boundary.
